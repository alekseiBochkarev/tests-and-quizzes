## 1. Цель плана

Довести продукт от рабочего учебного контура до **публичного MVP**, а затем —
до устойчивого развития. План нарезан так, чтобы задачи из разных потоков можно
было брать **параллельно**, не блокируя друг друга и не создавая конфликтов в
коде, схеме БД и миграциях.

Главный принцип: **параллельность по зонам ответственности, последовательность по
зависимостям**. Если две задачи трогают один и тот же файл или одну и ту же
таблицу — они не берутся одновременно.

---

## 2. Приоритеты

| Приоритет | Значение | Когда делать |
|---|---|---|
| **P0** | Без этого нельзя показывать продукт людям и запускать бету | Волны 1–2 |
| **P1** | Нужно для полноценного MVP, но можно выпустить чуть позже | Волны 2–3 |
| **P2** | Развитие после MVP | Волны 3–4 |
| **P3** | Эксперименты и партнёрства | После MVP |

**Оценка** — в person-days для одного исполнителя, включая тесты и документацию.
Для команды из 2–3 человек календарные сроки сжимаются, но не суммируются
напрямую: часть задач требует ревью и согласования контрактов.

## 7. Правила параллельной работы

### 7.1. Одна задача — одна ветка — один PR

- Ветка: `task/<id>-<краткое-имя>`, например `task/lrn-01-quiz-releases`.
- PR не смешивает две задачи, даже если они «рядом».
- PR содержит: код, тесты, обновление документации и план отката, если есть
  миграция.

### 7.2. Миграции — «поезд»

`prisma/schema.prisma` — самый конфликтный файл. Правила:

1. Одна задача с миграцией за раз в волне.
2. Только аддитивные изменения: новые таблицы, nullable-поля, индексы. Удаления
   и переименования — отдельной поздней миграцией.
3. Не редактировать уже применённые миграции.
4. Порядок merge в волнах:
   - Волна 1: `LRN-01`;
   - Волна 2: `GRW-02` → `GST-01` → `LRN-02`;
   - Волна 3: `CNT-05` → `GST-02`.
5. Перед merge: `npm run db:generate`, `npm run db:test:deploy`, полный e2e.

### 7.3. Общие файлы

| Файл / зона | Владелец в волне | Правило |
|---|---|---|
| `prisma/schema.prisma` | задача с миграцией | Только по «поезду», см. §7.2 |
| `.github/workflows/ci.yml` | **OPS-01** | Остальные просят изменения через OPS-01 |
| `components/layout/SiteHeader.tsx` | **ACC-03** | Новые ссылки — через ACC-03 |
| `app/account/page.tsx` | **ACC-01** → **ACC-02** | Не параллелить; достижения/дипломы — отдельными компонентами |
| `app/attempts/[id]/result/page.tsx` | **GRW-01** → **LRN-01** | Сначала шаринг, потом выпуски |
| `lib/ui/text.ts` | **LRN-02** | Остальные добавляют свои ключи точечно |
| `app/layout.tsx` | **ACC-03** | Cookie-баннер и провайдеры — через ACC-03 |

### 7.4. Контракты API

- Сначала фиксируем запрос/ответ в Zod-схеме и типах, потом делаем UI.
- Ошибки — в общем формате `{ error: { code, message, details? }, requestId }`.
- Новые админские роуты — только `/api/v1/admin/*`, без смешивания с публичными.
- Для каждой мутации: same-origin, сессия, rate-limit, `no-store`.

### 7.5. Фича-флаги

Незаконченные механики (гость, достижения, дипломы, письма) скрываются за
env-флагом вида `FEATURE_GUEST_MODE=0`. Это позволяет мержить код в `master`, не
показывая сырой функционал пользователям.

## 8. Definition of Ready

Задачу можно брать в работу, если:

- [ ] есть результат для пользователя, а не только «сделать модель»;
- [ ] написаны acceptance criteria;
- [ ] понятно, меняется ли схема БД и какая миграция;
- [ ] описан контракт API или компонента;
- [ ] указаны затронутые файлы и поток;
- [ ] есть тестовый сценарий;
- [ ] учтены доступность 55+ и тексты интерфейса;
- [ ] есть оценка и зависимость от других задач.

## 9. Definition of Done

- [ ] Код в `master`, CI зелёный.
- [ ] Unit-тесты на новую логику; e2e/интеграционные — где нужно.
- [ ] `lint`, `typecheck`, `test`, `build` локально зелёные.
- [ ] Миграция применяется на чистой БД и на тестовой.
- [ ] Обновлены README/документы, если изменилось поведение.
- [ ] Проверены пустые состояния, ошибки сети и повторная отправка.
- [ ] Проверена доступность: фокус, подписи, контраст, размер текста.
- [ ] Нет `console.log`, `any` без обоснования, секретов в коде.
- [ ] Для фичи есть метрика или событие (если применимо).
- [ ] Есть план отката для миграции/деплоя.

## 11. Что не делаем сейчас

- Live-тесты, дуэли, PvP, матчмейкинг.
- Публичные рейтинги и лиги.
- UGC: пользовательские вопросы и публичные профили.
- Мобильное приложение, Telegram Mini App, PWA — после MVP.
- B2B-кабинет учителя/компании.
- Платежи и рекламу — до подтверждённого удержания.
- Сложную адаптивную модель и ML-рекомендации — сначала данные.
