# CNT-01. Импорт вопросов из forms_writer

> **ID:** `CNT-01`
>
> **Статус:** реализовано 23.11.2026. Миграции не нужны.
>
> **Поток:** B. CONTENT. Зависимостей нет. Совместимо с A, C, D, E, F.

---

## 1. Зачем

До этой задачи каталог наполнялся только демо-набором из репозитория
(122 вопроса с `Question.isDemo = true`). Реальный конвейер `forms_writer` уже
отдаёт готовые вопросы в JSON, но перенести их в продукт было нечем.

Теперь наполнение выглядит так: `forms_writer` → JSON → CLI-импорт → каталог.
Схема БД и публичные страницы не меняются.

---

## 2. Формат входа

Импорт принимает файлы `forms_writer` без переименования полей:

```json
{
  "questions": [
    {
      "topic": "История",
      "question": "В каком году пала Западная Римская империя?",
      "options": ["395", "410", "476", "1453"],
      "correct_index": 2,
      "context": "Последнего императора звали Ромул Августул…",
      "explanation": "В 476 году Одоакр низложил Ромула Августула…"
    }
  ]
}
```

Принимается и голый массив вопросов. Поля `context` и `explanation` могут быть
пустыми строками — это штатное поведение генератора.

---

## 3. Маппинг тем

`scripts/import/topic-map.json` переводит плоскую тему файла в пару
«раздел / тема» каталога:

```json
{
  "version": 1,
  "topics": {
    "История": { "category": "nauka", "topic": "history" }
  }
}
```

Правила:

- неизвестная тема — ошибка, а не автоматическое создание мусорной темы;
- `category` и `topic` — slug-и (строчная латиница, цифры, дефис);
- `version` должен быть равен `1`; другая версия — ошибка, чтобы старый CLI не
  читал новый формат «как получится»;
- несколько исходных тем могут вести в одну тему каталога (например, «Физика»
  и «Химия» → «Точные науки»);
- отсутствующая тема создаётся только с флагом `--create-topics`; `title`
  берётся из маппинга, иначе — из исходного названия темы.

---

## 4. Правила импорта

### 4.1. Дедупликация по `contentHash`

Хеш считается как SHA-256 от версии схемы, темы, нормализованного текста
вопроса, отсортированных нормализованных вариантов и текста правильного ответа.

- порядок вариантов не влияет: `forms_writer` перемешивает ответы;
- регистр, «ё/е», кавычки, тире, лишние пробелы и завершающая пунктуация не
  создают «новый» вопрос;
- тема входит в хеш: одинаковый вопрос в разных темах — не дубликат.

Повторный импорт находит вопрос по `(topicId, contentHash)` и:

- ничего не меняет, если текст объяснения и статус совпали → `пропущено`;
- обновляет `explanation`/`status`, поднимает `version` → `обновлено`.

### 4.2. Версии и защита опубликованного

`contentHash` не включает объяснение, поэтому правка объяснения — это
`обновлено`. Если же при том же тексте изменился набор вариантов или правильный
ответ, хеш другой, и импорт считает это **новой версией**:

1. предыдущая версия с тем же нормализованным текстом переводится в `ARCHIVED`;
2. создаётся новый вопрос с `version = 1` и `isDemo = false`;
3. в отчёте это `replaced` и предупреждение `new_version`.

Так пользователь не видит две «правильные» формулировки одного вопроса, а
прогресс не привязывается к устаревшему тексту. Старые ответы и
`QuestionProgress` остаются в истории, но архивированный вопрос не входит в
`totalQuestions` (см. §4.6).

Изменение самого текста — отдельный случай: у `forms_writer` нет стабильного
идентификатора вопроса, поэтому импорт не может отличить исправление
формулировки от нового вопроса. Чтобы не угадывать, CLI создаёт новый вопрос, а
старый оставляет как есть и выдаёт предупреждение `possible_duplicate_text`,
если текст похож на существующий. Решение «оставить оба или архивировать
старый» принимает редактор. Если с таким текстом есть только архивный вопрос,
создаётся новая версия с предупреждением `archived_version` — это подсказка не
отменять решение редактора молча.

Защита от тихого снятия с публикации:

- если в файле у вопроса нет объяснения (`DRAFT`), а такой же вопрос уже
  опубликован — черновик **не применяется**, опубликованная версия остаётся;
- вопрос в `ARCHIVED` не публикуется повторно: архив — решение редактора,
  импорт его не отменяет;
- демо-вопросы не считаются «предыдущей версией»: реальный вопрос с тем же
  текстом создаётся отдельно, а демо скрывается отдельным шагом (§4.5).

### 4.3. Валидация

Вопрос отклоняется с ошибкой, если:

- тема пустая или отсутствует в маппинге (`empty_topic`, `unknown_topic`);
- текст вопроса пустой (`empty_question`);
- вариантов не ровно 4, есть пустой или повторяющийся вариант (`options_count`,
  `empty_option`, `duplicate_option`);
- `correct_index` — не целое число в диапазоне вариантов
  (`invalid_correct_index`);
- раздел из маппинга отсутствует в каталоге (`unknown_category`);
- темы из маппинга нет в каталоге, а `--create-topics` не указан
  (`topic_not_found`);
- тема уже существует в другом разделе (`topic_category_mismatch`): молча
  переносить тему нельзя, нужно исправить `topic-map.json`.

Предупреждения (импорт продолжается):

| Код | Когда |
|---|---|
| `missing_explanation` | нет объяснения: новый вопрос станет `DRAFT`, опубликованный останется как есть |
| `duplicate_in_file` | вопрос повторяет предыдущий в файле; остаётся версия с объяснением |
| `conflicting_duplicate` | тот же текст, но другие варианты или ответ; вопрос пропущен |
| `topic_archived` | тема не опубликована: вопросы загрузятся, но их никто не увидит |
| `existing_question` | вопрос уже есть и оставлен как есть (архив, черновик против публикации) |
| `new_version` | создана новая версия, старая формулировка в архиве |
| `archived_version` | создана новая версия при архивном предыдущем вопросе: проверьте, не отменяет ли это решение редактора |
| `possible_duplicate_text` | текст похож на существующий вопрос: возможно, это правка формулировки |
| `duplicate_hash` | в теме уже несколько вопросов с одинаковым хешем; обновлён первый |

Ошибки в отчёте содержат номер вопроса, тему и причину. Валидные вопросы
загружаются, даже если в файле есть ошибки, — но код завершения будет `1`.
Флаг `--strict` меняет это: при любой ошибке транзакция откатывается целиком.

### 4.4. Вопросы без объяснения

`Question.explanation` обязателен: объяснение показывается после ответа. Если
генератор не дал объяснение, вопрос сохраняется со статусом `DRAFT`: он лежит в
базе, но не попадает в каталог и тренировки, пока редактор его не дополнит.
Черновик не заменяет уже опубликованный вопрос (см. §4.2).

### 4.5. Демо-контент

Импортированные вопросы всегда `isDemo = false`. Если в теме после импорта есть
хотя бы один опубликованный реальный вопрос, все опубликованные демо-вопросы
этой темы переводятся в `ARCHIVED`. Данные не удаляются, поведение обратимо.
Демо-вопросы не участвуют и в дедупликации: реальный вопрос, совпавший с демо по
тексту и вариантам, создаётся отдельной строкой, а не «растворяется» в демо.

`npm run db:seed` больше не возвращает `status`/`isDemo` при upsert, поэтому
повторный сид не «воскрешает» скрытые демо-вопросы.

Флаг `--keep-demo` отключает скрытие — нужен только для отладки.

### 4.6. Пересчёт прогресса и транзакция

Импорт меняет `totalQuestions` темы, а скрытие демо — ещё и состав вопросов.
Поэтому после записи CLI пересчитывает `TopicProgress` для всех пользователей,
у которых он уже есть: `totalQuestions` по опубликованным вопросам,
`QuestionProgress` — только по опубликованным. Иначе каталог и «Мои результаты»
показывали бы разные цифры. Пользователи без `TopicProgress` не создаются.

Все изменения идут одной транзакцией. При ошибке БД выполняется `ROLLBACK`, база
остаётся в исходном состоянии. `--dry-run` ничего не пишет, но показывает
будущие счётчики, включая архивацию демо.

Уникального индекса на `(topicId, contentHash)` нет намеренно: схема БД в
CNT-01 не меняется, а исторические дубли (если появятся) нужно сначала
разобрать вручную. Если в теме окажется несколько вопросов с одинаковым хешем,
CLI предупредит и обновит первый — молчаливой правки не будет.

## 5. CLI

```powershell
# Проверить план без записи
npm run db:import -- --file ../forms_writer/samples/questions.json --dry-run

# Загрузить и создать отсутствующие темы
npm run db:import -- --file ./batch-2026-11.json --create-topics

# Загрузить только если все вопросы валидны (для CI и релизной партии)
npm run db:import -- --file ./batch.json --strict

# Сохранить отчёт для контент-команды
npm run db:import -- --file ./batch.json --report logs/import-report.json
```

| Опция | Назначение |
|---|---|
| `--file <path>` | JSON-файл `forms_writer` (обязательно) |
| `--map <path>` | маппинг тем, по умолчанию `scripts/import/topic-map.json` |
| `--dry-run` | показать план без записи в БД |
| `--create-topics` | создавать отсутствующие темы из маппинга |
| `--keep-demo` | не скрывать демо-вопросы |
| `--strict` | откатить всё, если есть ошибки валидации |
| `--json` | только JSON-отчёт для CI |
| `--report <path>` | сохранить отчёт в файл |
| `--help` | справка |

Отчёт содержит: `ok / strict / counts` (`total / created / updated / replaced /
skipped / notImported / draft / demoArchived / withContext /
progressRecalculated / errors / warnings`), разбивку по темам, массив `contexts`
(«завязки», которые пока не хранятся в БД) и список `issues` с кодами, темой и
номером вопроса.

Коды завершения:

- `0` — ошибок нет (предупреждения допустимы);
- `1` — были ошибки валидации, отсутствующая тема/раздел или `--strict`
  откатил изменения.

`--json` печатает отчёт и при пустом плане, и при фатальной ошибке
(`{"ok": false, "error": "...", "counts": ..., "issues": [...]}`), чтобы CI не
разбирал текст. При `--strict` отчёт с `issues` сохраняется и при откате
транзакции — по нему видно, что именно помешало партии.

`context` («завязка» из `forms_writer`) пока не хранится в БД: CLI выводит,
сколько вопросов его содержат, и складывает сами «завязки» в отчёт. Решение о
поле `Question.hint` относится к LRN-01, чтобы не плодить миграции вне «поезда».

## 7. Критерии приёмки

- [x] импорт принимает файлы `forms_writer` без ручного переименования полей;
- [x] дубликаты определяются по `contentHash`;
- [x] у каждого вопроса 4 варианта и ровно один правильный;
- [x] ошибки показывают тему, номер вопроса и причину;
- [x] повторный импорт не создаёт дубликаты;
- [x] есть `--dry-run` и отчёт «создано / обновлено / пропущено»;
- [x] вопросы без объяснения не попадают в каталог (`DRAFT`);
- [x] черновик не снимает с публикации уже опубликованный вопрос;
- [x] изменение вариантов/правильного ответа создаёт новую версию, старая уходит в архив;
- [x] изменение текста не создаёт молчаливый дубль: выводится `possible_duplicate_text`;
- [x] тема из маппинга с другим разделом не переносится молча (`topic_category_mismatch`);
- [x] `context` попадает в отчёт, хотя в БД пока не сохраняется;
- [x] демо-вопросы скрываются в темах с реальным контентом;
- [x] `TopicProgress` пересчитывается после импорта;
- [x] есть `--strict` для атомарной загрузки партии;
- [x] схема БД не менялась.

## 9. Что не входит

- Импорт и редактирование через админку (CNT-04).
- Публикация черновиков и редакционный workflow (CNT-05).
- Факт-чек содержимого (CNT-06).
- Хранение и показ `context` как подсказки (LRN-01).
- Поддержка `true_false` и `image_single_choice` (LRN-04).
