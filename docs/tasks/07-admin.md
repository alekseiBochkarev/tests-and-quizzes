## 1. Зачем

До этой задачи управлять контентом можно было только сидом и CLI-импортом.
Нужен защищённый служебный раздел, куда можно постепенно добавлять управление
темами, вопросами, выпусками и импортом, не смешивая его с публичным сайтом.

Задача даёт:

- единый вход в админку для редакторов и администраторов;
- серверную проверку роли на всём сегменте `/admin`;
- навигацию и понятные заглушки будущих разделов;
- безопасную выдачу роли без публичного HTTP-эндпоинта;
- тесты на все четыре состояния: гость, пользователь, редактор, администратор.

## 2. Продуктовые решения

| Вопрос | Решение |
|---|---|
| Кто видит админку | Только `EDITOR` и `ADMIN` |
| Что видит редактор | Обзор, темы и вопросы, выпуски, импорт |
| Что видит администратор | Все разделы, включая пользователей и аналитику |
| Что видит обычный пользователь | Ничего: `/admin` отвечает `404` |
| Что видит гость | Перенаправление на `/login?next=%2Fadmin` |
| Ссылка в шапке | «Админка» только для сотрудников |
| Выдача роли | CLI `npm run user:role -- <email> <роль>` |
| Смена роли через сайт | Пока нет; появится отдельной задачей |
| Аудит действий | Пока нет; появится в CNT-05 |
| Миграция БД | Не нужна |

Обычный пользователь получает `404`, а не `403`: служебный раздел не должен
рекламировать своё существование. Гость же получает понятный вход, потому что
после входа сможет вернуться в админку.

## 3. Роли и матрица доступа

Роли уже описаны в `prisma/schema.prisma`:

```prisma
enum UserRole {
  USER
  EDITOR
  ADMIN
}
```

| Маршрут | Гость | `USER` | `EDITOR` | `ADMIN` |
|---|---|---|---|---|
| `/` и публичные страницы | да | да | да | да |
| `/admin` | вход | `404` | да | да |
| `/admin/topics` | вход | `404` | да | да |
| `/admin/quizzes` | вход | `404` | да | да |
| `/admin/import` | вход | `404` | да | да |
| `/admin/users` | вход | `404` | `404` | да |
| `/admin/analytics` | вход | `404` | `404` | да |

Правила сосредоточены в трёх модулях:

- `lib/auth/roles.ts` — `isStaffRole`, `isAdminRole`, `isUserRole`, `roleLabel`;
- `lib/admin/nav.ts` — единый список разделов и `visibleAdminNav`;
- `lib/auth/admin.ts` — серверные `requireStaff` и `requireAdmin`.

`visibleAdminNav` возвращает пустой список всем, кроме сотрудников. Это защищает
от случайной выдачи ссылок, но не является защитой доступа: проверка всегда
выполняется на сервере.

## 4. Серверные правила

`app/admin/layout.tsx` вызывает `requireStaff()` для всего сегмента. Поэтому
каждая вложенная страница закрыта одним guard, даже если о ней забыли отдельно.

`requireStaff(nextPath = "/admin")`:

1. читает текущего пользователя через `getCurrentUser()`;
2. гостя перенаправляет на `/login?next=<nextPath>`;
3. пользователя без staff-роли отправляет в `notFound()`.

`requireAdmin(nextPath)` дополнительно требует роль `ADMIN`. Его вызывают
страницы `users` и `analytics`, поэтому редактор получает `404`, даже если
откроет адрес напрямую.

Роль читается из БД на каждом запросе, а не хранится в cookie. После изменения
роли через CLI пользователю достаточно обновить страницу — повторный вход и
сброс сессии не нужны. Понижение роли действует так же сразу.

Других изменений в auth-контуре задача не делает:

- новых cookie и полей сессии нет;
- `sessionEpoch` не меняется;
- публичного endpoint смены роли нет;
- админские API-роуты появились в CNT-04 и живут отдельно в `/api/v1/admin/*`.

## 5. Маршруты и интерфейс

| Маршрут | Содержимое |
|---|---|
| `/admin` | Обзор: что уже работает и карточки доступных разделов |
| `/admin/topics` | Темы и вопросы: CRUD, публикация и архив (CNT-04) |
| `/admin/quizzes` | Заглушка «Выпуски» |
| `/admin/import` | Импорт JSON с предпросмотром (CNT-04) |
| `/admin/users` | Заглушка «Пользователи», только `ADMIN` |
| `/admin/analytics` | Заглушка «Аналитика», только `ADMIN` |

Общие элементы:

- `app/admin/layout.tsx` — заголовок «Админка», подпись роли и email, навигация,
  ссылка «Вернуться на сайт»;
- `components/admin/AdminNav.tsx` — клиентская навигация с `aria-current="page"`;
- `components/admin/AdminPlaceholder.tsx` — единый вид заглушки: что будет в
  разделе и какая задача это сделает;
- `components/layout/SiteHeader.tsx` — ссылка «Админка» только для `EDITOR` и
  `ADMIN`;
- `app/admin/layout.tsx` и страницы объявлены `force-dynamic` с `revalidate = 0`,
  чтобы роль и содержимое не кешировались;
- у админки `robots: { index: false, follow: false }`.

Интерфейс — по-русски, без «XP», «mastery», «streak», «лидерборд» и «квиз».
Кнопки и пункты навигации не ниже 56 px, крупный текст, видимый фокус,
`aria-current` для активного раздела.

## 6. CLI выдачи роли

```powershell
npm run user:role -- user@example.com EDITOR
npm run user:role -- user@example.com ADMIN
npm run user:role -- user@example.com USER
```

Скрипт `scripts/user-role.mjs`:

- нормализует email в lowercase и ищет по `emailNormalized`;
- принимает только `USER`, `EDITOR`, `ADMIN`;
- обновляет `role` и `updatedAt` у неудалённого пользователя;
- идемпотентен: повторный запуск с той же ролью не ломает данные;
- не читает и не печатает пароли, токены и хеши;
- при неизвестной роли, отсутствии `DATABASE_URL` или ненайденном пользователе
  завершается с кодом `1` и понятным сообщением.

Публичного HTTP-эндпоинта для смены роли нет: выдача роли требует доступа к
базе или серверу.

## 7. Тесты

### Unit

`tests/unit/auth/roles.test.ts` — 8 тестов:

- `isStaffRole` пускает `EDITOR` и `ADMIN`, не пускает `USER`, пустые значения и
  роли в другом регистре;
- `isAdminRole` пускает только `ADMIN`;
- `isUserRole` распознаёт значения схемы;
- `roleLabel` возвращает понятные русские подписи;
- `visibleAdminNav` скрывает пользователей и аналитику от редактора и не отдаёт
  разделы обычному пользователю и гостю.

### E2E

`tests/e2e/admin-access.spec.ts` — 4 сценария:

1. гость открывает `/admin` и попадает на `/login?next=%2Fadmin`;
2. обычный пользователь не видит ссылку «Админка», а `/admin` отвечает `404`;
3. редактор видит контентные разделы, не видит «Пользователи» и «Аналитика»,
   а прямой заход в `/admin/users` получает `404`;
4. администратор видит все разделы и открывает «Пользователи».

Роль в тестах меняется helper-ом `setUserRole` из `tests/e2e/helpers.ts`: он
запускает CLI с `DATABASE_URL=DATABASE_URL_TEST` и отказывается работать, если
строка подключения указывает на dev-БД `quiz`.

Проверки задачи:

```powershell
npm run lint
npm run typecheck
npm test
npm run build
$env:CI="true"; npm run test:e2e
```

## 10. Откат

Миграции нет, данные менять не нужно. Безопасный откат:

1. убрать ссылку «Админка» из `components/layout/SiteHeader.tsx`;
2. удалить `app/admin/`, `components/admin/`, `lib/admin/`, `lib/auth/admin.ts`
   и `lib/auth/roles.ts`;
3. удалить `scripts/user-role.mjs` и npm-скрипт `user:role`;
4. удалить тесты `tests/unit/auth/roles.test.ts`, `tests/e2e/admin-access.spec.ts`
   и helper `setUserRole`.

Роли `EDITOR`/`ADMIN` в базе можно оставить: без админки они ни на что не влияют.
Если нужно вернуть всех в `USER`:

```sql
UPDATE "User" SET role = 'USER' WHERE role IN ('EDITOR', 'ADMIN');
```

Учебные данные, попытки и прогресс при откате не затрагиваются.
